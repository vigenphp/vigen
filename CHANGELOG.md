# Changelog

All notable changes to Vigen will be documented in this file.

## [Unreleased]

## [1.0.2] - 2026-09-17

### Fixed

- **`vigen migrate` failed on the first run against any empty database.** `Migrator::applied()` read the `migrations` bookkeeping table without making sure it existed - the `ensureRepository()` call lived only in `run()`, `runFile()` and `rollback()`. But `MigrateCommand::runPending()` asks `pending()` for its work list *before* it runs anything, and `pending()` is built on `applied()`, so `vigen migrate` on a fresh project died with `SQLSTATE[42S02]: Base table or view not found: Table 'vigen.migrations' doesn't exist` (or "no such table: migrations" on SQLite) before a single migration file could create it. `ensureRepository()` is now called from `applied()`, which every reader of that table - `pending`, `isApplied`, `migrate status`, `rollback` - goes through. This was the first command a new project runs, on every driver, and no test caught it because every existing `MigratorTest` case called `run()` first, creating the table before the read; two regression tests now cover a virgin database.

## [1.0.1] - 2026-09-17

### Fixed

- **Models were generated with no migration, so the tables never existed.** `ApiReference` documented the migration *file shape* but nothing said *when* one is required - and unlike a controller's `View::render()` reference, a model never mentions its migration anywhere, so the existing "every file you reference must be included in this same response" rule could not catch it. `vigen chat "Create a user management system"` wrote the model, both controllers, the routes and all five views, and no migration at all: `php vigen migrate` had nothing to run, and the first query failed with "no such table". `ApiReference::migrationRule()` now states the pairing the way the view/route rule already does - creating a model, or adding a column to one, requires its `CREATE TABLE` / `ALTER TABLE` migration in the same response - and the planner's own rules list repeats it in brief.

## [1.0.0] - 2026-09-16

### Added

- **An HTTP runtime.** Vigen previously had no way to *serve* the code it generated: nothing read `routes/web.php`, and `vigen serve` started the chatbox. Generated routes therefore 404'd in a browser no matter how correct they were. The framework now has a real request lifecycle, entered through `public/index.php`:
  - `Vigen\Http\Request` / `Response` - request built from PHP's globals (form posts and JSON bodies alike), immutable response with `html`/`text`/`json`/`redirect`/`noContent` factories.
  - `Vigen\Http\Router` - `get`/`post`/`put`/`patch`/`delete` on a `$router` variable placed in scope for the route file, `{param}` captures matched to action parameters **by name** and optional as `{param?}`, middleware alias lists, 404 and 405 handling.
  - `Vigen\Http\Kernel` - boots the session, loads the route file, runs the middleware pipeline, autowires the controller, dispatches, and translates exceptions into responses. Unhandled exceptions are logged to `storage/logs/vigen.log`.
  - `Vigen\Http\Session` - static API over the PHP session, with flash values that survive exactly one request, a CSRF token, and id rotation on login/logout.
  - `Vigen\Http\Validator` - the rule set behind `$request->validate()`, including `unique`/`exists` against the database. Unknown rule names throw rather than passing silently.
  - `Vigen\View\View` - plain-PHP templates resolved by dotted name from `resources/views/`, rendering to a `Response`, with `e()` escaping and `View::error()`/`errors()`/`old()` for form re-display.
  - `Vigen\Core\Container` - reflection autowiring for controller constructor dependencies.
  - `src/Support/helpers.php` - the globals `e()`, `env()`, `config()`, `base_path()`, loaded through Composer's `autoload.files`.
- **A data layer.** `Vigen\Database\Connection` (lazy PDO; SQLite by default, MySQL via `.env`; `select`, `statement`, `transaction`), `QueryBuilder` (fluent, every value bound, identifiers validated and quoted per driver), `Model` (active record with `$fillable` as a hard allow-list, `$hidden` respected by `toArray()`, automatic timestamps), and `Migrator`.
- **Auth.** `Vigen\Auth\Hash` (`make`/`check`/`needsRehash`), `Vigen\Auth\Auth` (session-backed guard: `attempt`, `login`, `user`, `check`, `id`, `logout`), and the `auth` / `guest` middleware. The session stores only the user id and the row is re-read per request, so a deleted account stops working immediately.
- `vigen migrate`, `migrate status`, `migrate rollback`, `migrate --fresh` - run the plain-SQL closures in `database/migrations/`, recording applied files so a re-run is a no-op.
- `vigen gui` - the chatbox, which is what `vigen serve` used to be. `vigen serve` now serves your application (`public/index.php`). `vigen serve --gui` prints a pointer to the new command rather than silently doing something different.
- `Vigen\AI\ApiReference` - the runtime API above, as text, embedded in both the planner and fixer system prompts. Reliability with a native (non-Laravel) API depends entirely on the model being told that API precisely.
- `Vigen\Project\CodeValidator` - parses each generated file and rejects references to classes Vigen does not provide (`Illuminate\`, `Laravel\`, `Symfony\`, `Doctrine\`, `Carbon\`, and the bare `Route`/`Hash`/`Auth`/`DB`/`Schema`/`Blade`/`Validator`/`Controller`/`Model`/`Migration`, plus Laravel's global helpers). Each error names the file, the line, and the Vigen replacement. This uses `nikic/php-parser`, which was a declared but entirely unused dependency.
- `Scaffolder` now publishes `public/index.php`, `config/database.php`, `config/auth.php`, `resources/views/welcome.php`, `resources/views/errors/404.php`, and a starter `routes/web.php`, and creates `public/`, `resources/views/`, `database/`, and `storage/logs/`. Every write is still `putIfMissing`.
- Docs: `routing.md`, `requests-and-responses.md`, `views.md`, `database.md`, `authentication.md`, plus a documentation index in the README.
- `tests/ScaffolderTest.php` - what a brand-new project gets: the directories the runtime writes to, the files a first request needs, the keys `config/app.php` must carry, that no write ever clobbers an edited file, and that the scaffolded `.env.example` actually configures `ProviderFactory` (the regression test for the `AI_PROVIDER` key mismatch above).

### Changed

- **`vigen serve` now runs your application, not the chatbox.** The chatbox moved to `vigen gui`. Both default to `127.0.0.1:8808`, so pass `--port` to run them together.
- **The planner prompt now carries Vigen's own API and an explicit "Vigen is not Laravel" rule.** This was the root cause of the generated code being unrunnable: the prompt supplied Laravel's directory conventions and never stated Vigen's runtime, and a model trained on Laravel obligingly wrote Laravel. `Conventions` still supplies the paths; `ApiReference` supplies the API.
- The planner prompt also states that browser-facing features need pages, not just endpoints - a `GET` route rendering a view for every `POST` handler, and the view file in the same response. An LLM's default answer to "create an authentication module" is a JSON API with no page a browser can open.
- `AIEngine::validate()` now runs `SyntaxValidator` **and** `CodeValidator`, so the single-retry fix loop finally fires on Laravel-flavoured output. `php -l` passes on that code, which is exactly why nothing complained before.

### Fixed

- **Every route defined with a closure fataled.** `Router::invoke()` called `$route->action(...$arguments)`, which PHP reads as a *method* call named `action()` - properties are never consulted for that form, and `Vigen\Http\Route` has no `__call` - so a closure route died with `Call to undefined method Vigen\Http\Route::action()`. That includes the `$router->get('/', fn () => View::render('welcome'))` in the scaffolded `routes/web.php`, so a brand-new project's home page failed on the first request. The closure is now copied to a local before it is called. Controller routes (`[Controller::class, 'method']`) were unaffected.
- **An optional route parameter could never match when it was absent.** `Router::compile()` appended the placeholder as `(?P<page>[^/]*)?` and joined the segments with `/`, so `/blog/{page?}` compiled to `#^/blog/(?P<page>[^/]*)?$#` - the slash in front of the optional group was still mandatory, and `/blog`, the one path the syntax exists to allow, was the one path that could not match. The separator now sits inside the group: `(?:/(?P<page>[^/]*))?`.
- **`Container::make()` returned cached instances.** It was written as `has($class) ? get($class) : build($class)`, so any class an earlier `get()` had cached came back from `make()` as the same object - the opposite of its documented contract. The router builds controllers with `make()`, so two requests could have shared one controller instance. `make()` now ignores `$instances` and builds fresh, while still honouring explicit bindings.
- **`Session::reset()` wrote null through a reference into the caller's array.** `Session::use()` binds the store by reference, so `self::$store = null` followed that reference out into the caller's variable - a fatal `TypeError: Cannot assign null to reference held by property ... of type array` whenever the binding array lived in a typed property. `reset()` now rebinds to a fresh variable, dropping the link rather than following it.
- **The `View::partial()` docblock prescribed code that fatally failed.** It showed `<?= View::partial('partials.header') ?>` for use inside a template, but a template is an included plain-PHP file with no namespace, so a bare `View::` resolves to the global `\View` and dies with "Class View not found". The docblock, the planner's API reference, and the test fixture now all use `\Vigen\View\View::partial(...)`.
- `#[RequiresPhpExtension('pdo_sqlite')]` on `DatabaseTest`, `KernelTest`, `MigratorTest` and `AuthTest`, so a PHP build without that driver reports four skipped classes naming the extension instead of forty identical "could not find driver" exceptions.
- **`vigen chat` never changed any files.** The prompt pipeline reported success and wrote nothing, on every provider and every model. Four independent defects each produced the same symptom, so even a perfect model response was discarded at four separate points:
  - `TaskPlan::fromProviderResponse()` read `$response['steps']`, a key that exists only in the `FakeProvider` test double. No real provider returns it - Ollama nests the answer under `message.content`, OpenAI under `choices[0].message.content`, Claude under a list of content blocks, Gemini under `candidates[0].content.parts`. The step list was therefore always empty. Response unwrapping now lives in `AbstractProvider::extractText()`, the one place that knows about vendor envelopes.
  - The planner prompt never specified an output format, so the model answered in prose. It now states an explicit JSON contract (`{"summary": ..., "files": [{"path", "action", "contents", "reason"}]}`) and asks the provider for structured output in its own native way (Ollama's `format: json`, OpenAI's `response_format`; Claude and Gemini rely on the prompt).
  - `AIEngine::generateChanges()` mapped plan steps straight to `FileChange` without ever asking the model for file *contents*, so every change had a null body. Planning and generation are now a single call whose steps carry complete file bodies.
  - Nothing applied changes to disk. `ChatCommand` printed `✓ {path}` cosmetically and `GUI\Server` returned a list; no applier existed anywhere in the AI path. New `Vigen\Project\FileWriter` performs the writes.
- **Generated code was written to disk unchecked, and the documented self-correction loop could never run.** `AIEngine::validate()` returned `ValidationResult::ok()` unconditionally, so `attemptFix()` was unreachable dead code - and it carried the same response-parsing bug. Validation is now real: `Vigen\Project\SyntaxValidator` runs `php -l` on every generated PHP file, failures feed the fix stage, and the loop retries once as documented. `--dry-run` lints the proposed bodies from a scratch directory so a preview still catches broken syntax.
- **An unusable model response looked like a successful no-op.** A response that could not be parsed, or one describing files with empty bodies, produced a cheerful "Done." with nothing written and no explanation - which is what made this so hard to diagnose. Unparseable responses, rejected plan entries, refused paths, and failed writes are now all reported by name, and the command exits non-zero.
- **Model-authored paths were written without validation.** Paths come from a language model and were previously used as-is, so a crafted prompt (or a poisoned file already in the project) could have steered a write to `../../.ssh/authorized_keys`. `FileWriter::resolve()` now normalises every path segment, refuses absolute and Windows drive/UNC paths, can never walk `..` above the project root, and protects Vigen's own `.vigen` directory.
- **The model could not see the files it was asked to modify.** `ProjectContext::relevantFiles()` returned paths only, so a request touching `routes/web.php` rewrote it from scratch and destroyed its contents. New `ProjectContext::relevantFileContents()` sends the bodies (capped, with truncation marked) instead.
- **Keyword matching in `relevantFiles()` matched against the absolute path**, so the project directory's own name matched every file in the tree. Because a Windows checkout always sits under `\Users\`, the keyword "user" returned the entire project. Matching is now against the project-relative path.
- Ollama reports failures such as an unknown model with an HTTP 200 and an `{"error": ...}` body; that is now raised as an error instead of being treated as an empty answer.
- **Plugin never activated.** `composer.json` declared `"type": "library"`, but Composer only activates a package's `extra.class` plugin when `"type"` is literally `"composer-plugin"` - so `VigenPlugin` silently never ran, on any install, ever. Confirmed with an isolated repro (a `type: library` package's plugin methods are never called, with no warning) before and after the fix. Changed to `"type": "composer-plugin"`.
- **Plugin missed the very first install.** Even with the type fixed, subscribing to `post-install-cmd`/`post-update-cmd` still missed a project's *first-ever* `composer require vigenphp/vigen`: Composer has a known "chicken and egg" limitation where a plugin installed within the same command that dispatches those events isn't registered in time to receive them (confirmed by reproduction; the same gap is documented in other Composer plugins, e.g. composer-merge-plugin#170). `./vigen` would only appear starting from a *second* `composer install`, breaking the documented `composer require` → `php vigen init` flow on first use. Fixed by doing the publish directly in `activate()`, which Composer calls immediately on the package's own installation, including the first. Verified end-to-end: `./vigen` now appears after a single, first-ever `composer install`, and re-installing never overwrites a customized script.
- Removed the `"bin": ["bin/vigen"]` declaration from `composer.json`. It collided with `vigenphp/installer`'s own `bin/vigen` whenever both were installed together (e.g. via `composer global require vigenphp/installer`, which requires this package) - Composer can only register one `vendor/bin/vigen` proxy, so it silently skipped one of them with a `name conflicts with an existing file` warning. The global `vigen` command name now belongs exclusively to `vigenphp/installer`; this package's `bin/vigen` is still present in the package and still runnable directly (`php vendor/vigenphp/vigen/bin/vigen ...`), just no longer auto-proxied by Composer.
- **`QueryBuilder::where()` and `Model::where()` took the operator third, not second**, so the natural `where('name', 'like', '%x%')` - Laravel's order, and therefore the order a generated controller writes - threw `Unsupported where operator [%x%]` at runtime. Both forms are now accepted: two arguments means `=` , three means the second is the operator.
- **A scaffolded `.env.example` configured nothing.** The stub wrote `AI_PROVIDER` / `AI_MODEL`, but `ProviderFactory` reads `VIGEN_AI_PROVIDER` / `VIGEN_AI_MODEL` (which `vigen init` writes correctly). A fresh project therefore silently fell back to Ollama with an empty model name - no error, just the wrong provider.
- **`vigen migrate --fresh` only worked on SQLite.** It issued `PRAGMA foreign_keys` unconditionally (a syntax error on MySQL) and listed tables with `SHOW TABLES` (MySQL-only). Both are now driver-aware, and PostgreSQL drops with `CASCADE`. The same SQLite-only DDL in `Migrator`'s `migrations` table is now written per driver.
- `vigen init` told GUI users to run `vigen serve`, which starts the *application* rather than the chatbox since the two commands were split. It now prints `vigen gui`, as do the install docs, the published `vigen` script's header, and a stale comment in `GUI\router.php`.
- **A missing PHP driver blamed your `.env`.** `Connection` reported every PDO failure as "could not connect to the [X] database: ... Check config/database.php and your .env", including `could not find driver` - which is not a configuration problem at all. It means the PHP build has no PDO driver for that database, and no edit to `.env` can fix it. That case is now reported separately: it names the extension to enable (`pdo_sqlite` / `pdo_mysql` / `pdo_pgsql`) and lists the drivers actually available.
- **The scaffolded `.env.example` omitted `DB_CONNECTION` from its MySQL instructions.** Its comment read "For mysql / pgsql, set these:" above a list containing only `DB_HOST`, `DB_PORT`, `DB_DATABASE`, `DB_USERNAME` and `DB_PASSWORD`. Filling in exactly those leaves the driver on `sqlite`, and the credentials are then ignored silently - the connection is attempted against a SQLite file named after the MySQL database. The comment now states that `DB_CONNECTION` has to change too.
- **Every command died with `Call to undefined function env()`** whenever the global helpers were not in Composer's generated `autoload_files.php`. That entry only takes effect when Composer regenerates the autoloader from *this package's* metadata, so a project requiring `vigenphp/vigen` picks it up from the released version it installed - a newer checkout, or a hand-copied `vendor/` directory, leaves the globals undefined even after `composer dump-autoload`. It is a hard fatal rather than a warning because `config/*.php` calls `env()` while `Config` is constructed, which is the first thing boot does. `Vigen\Core\Application` now requires `src/Support/helpers.php` itself when `env()` is not already defined, making boot independent of the generated autoloader.

- `Vigen\Project\SyntaxValidator` - `php -l` validation of generated files, and of proposed file bodies for dry runs.
- `Vigen\Project\FileWriter` and `WriteResult` - apply planned changes to disk, reporting per file whether it was created, modified, deleted, unchanged, rejected, or failed.
- `vigen chat --dry-run` - plan and validate without writing anything.
- Automatic backups: anything overwritten or deleted is copied to `.vigen/backups/<timestamp>/<path>` first, and `Scaffolder` now adds that directory to `.gitignore`.
- `phpunit.xml`, plus test coverage for response unwrapping across all four provider envelopes, plan parsing (fenced JSON, prose-wrapped JSON, trailing commas, rejected entries), the file applier (including path-traversal refusal), syntax validation, project context, and the engine end-to-end. The package previously had no PHPUnit configuration at all, so its tests had never been runnable as checked in.
- Companion package `vigenphp/installer` (separate repo/zip): global `composer global require vigenphp/installer` gives a `vigen create <name>` command, like `laravel/installer`'s `laravel new`. Reuses `Scaffolder`, `EnvWriter`, and `ProviderModels` from this package rather than duplicating the wizard logic.
- File-location conventions (`Vigen\Project\Conventions`, default: `app/Models`, `app/Http/Controllers`, `routes/web.php`, `database/migrations`, ...) are now generated into `config/app.php` on init and read by `AIEngine`, which tells the planner where to place generated files. Overridable per-project via `config('app.paths')`.
- `Vigen\Core\Config` - a small dot-notation loader for `config/*.php`.
- Composer plugin (`Vigen\Composer\VigenPlugin`) that auto-publishes a root-level `vigen` script on `composer require`/`update` - the Vigen equivalent of Laravel's `artisan`, so the primary CLI entry point is `php vigen ...` instead of `vendor/bin/vigen ...`. Never overwrites an existing `./vigen`.
- `vigen init` interactive setup wizard: choose CLI or GUI, default AI provider, and model; writes `.env` and scaffolds the project (`ProviderModels`, `Scaffolder`, `EnvWriter`).
- `vigen serve` command launching the built-in GUI chatbox via PHP's built-in server (`src/GUI/router.php`). Renamed to `vigen gui`; `serve` now runs the application.
- Initial repository scaffold: `src/Core`, `src/AI`, `src/CLI`, `src/GUI`, `src/Providers`, `src/Project`.
- Provider abstraction (`AIProviderInterface`) with Ollama, OpenAI, Claude, and Gemini implementations.
- `ProviderFactory` for resolving the configured provider from `.env`.
- `AIEngine` implementing the context → plan → generate → validate → fix workflow.
- `ProjectContext` for collecting project state relevant to a task.
- `vigen chat "<prompt>"` CLI command.
- Minimal GUI chatbox sharing the same `AIEngine` via `GUI\Server`.
- Composer package skeleton (`vigenphp/vigen`).
